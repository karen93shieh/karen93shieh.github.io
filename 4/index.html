Project 4: Neural Radiance Fields (NeRF)

Calibrating my own camera, fitting neural fields to 2D images, and training NeRFs for both the Lego scene and my plushies.

  • Course: CS180
  • Date: Nov 2025

Project Overview

This project explores Neural Radiance Fields (NeRF) from the ground up. I started by calibrating my own camera with ArUco tags, estimating camera intrinsics and poses, and packaging a real-world 3D scan into an npz dataset.

From there, I implemented a 2D neural field that learns to represent a single image using an MLP with sinusoidal positional encoding. I then extended this framework to 3D by building a NeRF for the Lego scene: constructing camera rays, sampling points along them, using an MLP to predict color and density, and implementing volume rendering in PyTorch.

Finally, I reused the same NeRF pipeline on my own captured dataset to generate novel views of a real object.

Part 0 — Calibrating Your Camera and Capturing a 3D Scan

Images Import

I started by loading two sets of images: calibration images from img/part_0_1_compressed and plush object images from img/part_0_2_compressed. Using Pillow's ImageOps.exif_transpose ensured EXIF orientation was normalized before converting to NumPy arrays. This preprocessing step is critical to avoid misaligned correspondences in later calibration steps.

Part 0.1 — Calibrating Your Camera

I collected a calibration dataset using a custom 2×3 grid of ArUco tags (DICT_4X4_50). The physical layout had:

  • Marker length: 60.0 mm
  • Horizontal separation: 90.0 mm
  • Vertical separation: 75.67 mm

Rather than using OpenCV's built-in GridBoard, I manually constructed the 3D coordinates for each marker ID to handle the custom spacing. For each calibration image, I detected ArUco corners and accumulated 2D–3D correspondences across all markers and all frames.

I then ran cv2.calibrateCamera with CALIB_USE_INTRINSIC_GUESS to estimate:

  • Camera intrinsics (K): focal lengths (fx ≈ 261.74, fy ≈ 265.12) and principal point
  • Distortion coefficients: radial and tangential distortion parameters
  • Reprojection error: ~0.66 pixels, indicating good calibration quality

I saved these calibration results to camera_calibration_compressed.json for reuse in subsequent steps. The calibration images show the 2×3 ArUco grid captured from different viewpoints, angles, distances, and tilts to ensure robust calibration across varying perspectives.

Part 0.2 — Capturing a 3D Object Scan

After calibration, I captured 59 images of my plush object. I placed a single ArUco tag (60 mm × 60 mm) in the scene and moved the camera around the object, covering a full orbit with variations in elevation.

The calibration from Part 0.1 provided the intrinsics matrix K and distortion coefficients, allowing me to treat all object images as views from a known, fixed camera model. This consistency is essential for accurate pose estimation. The captures show the plush object from various angles: frontal view with ArUco tag visible, side angle showing object geometry, different elevations and rotations, completing full orbital coverage around the object.

Part 0.3 — Estimating Camera Pose

For each object image, I detected the single ArUco tag and used cv2.solvePnP with the known 3D tag corners (a 60 mm square in the world coordinate system) and their 2D projections. This gave me a rotation vector (rvec) and translation vector (tvec) for each view.

I converted each (rvec, tvec) pair into a 4×4 camera-to-world matrix c2w by:

  1. Converting rvec to a rotation matrix R_w2c using cv2.Rodrigues
  2. Transposing to get R_c2w = R_w2c.T
  3. Computing the camera position: t_c2w = -R_c2w @ tvec
  4. Assembling into a homogeneous 4×4 matrix compatible with NeRF conventions

To visualize and validate these poses, I used Viser to render camera frustums in 3D. I computed the field of view from the intrinsics and added each camera with its corresponding image. This real-time visualization helped me identify and discard any frames with poor pose estimates. The visualizations show front/side views, top-down view, bottom-up view, and coordinate view, all revealing the circular camera trajectory around the object.

Part 0.4 — Undistorting Images and Creating a Dataset

With intrinsics, distortion coefficients, and poses estimated, I processed each object image:

  1. Detected the ArUco tag and computed its pose using cv2.solvePnP
  2. Undistorted the image using cv2.undistort with the calibrated parameters
  3. Converted from BGR to RGB for consistency with NeRF training pipelines
  4. Stored the undistorted image and corresponding c2w matrix

I then split the data deterministically: every 8th frame went to validation/test, and the rest to training. This yielded:

  • Training: 46 frames
  • Validation: 7 frames
  • Test: 7 poses (same as validation)

Finally, I computed the average focal length from fx and fy (≈263.43 pixels) and packaged everything into nerf_dataset_compressed.npz with the same structure as the Lego dataset:

  • images_train, c2ws_train
  • images_val, c2ws_val
  • c2ws_test
  • focal (scalar focal length)

Implementation Details & Rationales

Images Import: Loading with Pillow and normalizing EXIF orientation before NumPy conversion prevents misaligned correspondences. Previewing the first few frames verifies ordering and exposure.

Part 0.1 – Calibrating Your Camera: Re-creating the physical 2×3 custom ArUco layout in code gives full control over mixed marker spacing, replacing GridBoard.matchImagePoints. Accumulating correspondences from every frame and running cv2.calibrateCamera recovers precise intrinsics and distortion coefficients.

Part 0.2 – Capturing a 3D Object Scan: Defining the single-tag 3D square in meters (0.06 m) ensures metrically consistent pose estimates. Initializing a Viser server provides real-time feedback to catch bad frames early.

Part 0.3 – Estimating Camera Pose: Detecting ArUco tags per frame, calling cv2.solvePnP, and inverting the world-to-camera transform produces camera-to-world (c2w) matrices needed by NeRF. Composing quaternions and frustum geometry for Viser visually validates both orientation and translation.

Part 0.4 – Undistorting & Packaging: Undistorting with exact calibration parameters and converting to RGB guarantees pixel-to-pose alignment. Splitting indices deterministically (every 8th frame), computing a scalar focal length, and exporting to nerf_dataset_compressed.npz matches the format expected by later NeRF assignments.

Part 1 — Fit a Neural Field to a 2D Image

In Part 1, I implemented a 2D neural field that learns a continuous mapping from normalized pixel coordinates (x, y) to RGB values. Instead of storing pixel values directly, the network learns a function that can be queried at any coordinate. The architecture uses an MLP with sinusoidal positional encoding to capture high-frequency image details.

Model Architecture

The neural field consists of two main components:

  • Positional Encoding: Transforms 2D coordinates into a 42-dimensional feature vector using sinusoidal functions at multiple frequency levels (L = 10). This encoding is crucial for capturing fine details that raw coordinates cannot represent.
  • MLP: Three hidden layers of 256 neurons each with ReLU activation, followed by a final layer with Sigmoid activation to constrain RGB outputs to [0, 1].

Training Progression

I trained the model by randomly sampling 10,000 pixels per iteration and minimizing MSE loss between predicted and ground-truth RGB values. Below are reconstructions at different iterations (1, 50, 100, 200, 500, 1000) for both the Fox image and the Doll image.

Hyperparameter Sweep: 2×2 Grid

To understand how model capacity and positional encoding frequency affect reconstruction quality, I trained four models with different combinations of:

  • L (Positional Encoding Frequency): [3, 10]
    • Lower L (3): Captures broader, smoother features but misses fine details
    • Higher L (10): Captures high-frequency content and sharp textures
  • Width (Hidden Layer Size): [64, 256]
    • Smaller width (64): Fewer parameters, faster training, may underfit
    • Larger width (256): More capacity to learn complex patterns

The hyperparameter sweep results show a 2×2 grid: top row uses L=3 (low frequency encoding), bottom row uses L=10 (high frequency). Left column uses Width=64 (low capacity), right column uses Width=256 (high capacity). The combination of L=10 and Width=256 produces the best reconstruction quality (PSNR: 25.95 dB), while L=3 with Width=64 shows the most blurring (PSNR: 23.14 dB).

Key Insights

Positional Encoding is Critical: Without high-frequency positional encoding (low L values), the network cannot capture fine details and produces blurry reconstructions. The sinusoidal encoding at multiple frequencies enables the MLP to learn high-frequency image content.

Model Capacity Matters: Wider networks (256 vs 64 neurons) provide more capacity to learn complex patterns, especially when combined with high-frequency encoding. However, the improvement from width alone is limited without sufficient positional encoding.

Training Dynamics: The model learns coarse features first (low frequencies) and gradually refines details (high frequencies). This is visible in the progression images where colors and shapes emerge before fine textures.

Continuous Representation: Unlike discrete pixel grids, this neural field represents the image as a continuous function. This enables querying at arbitrary resolutions and smooth interpolation between coordinates, which is foundational for extending to 3D NeRF in Part 2.

Part 2 — Fit a Neural Radiance Field from Multi-view Images

In Part 2, I moved from 2D neural fields to a full 3D NeRF for the Lego dataset. The goal is to reconstruct a continuous radiance field from multi-view images and then render novel views.

Part 2.1 — Create Rays from Cameras

I implemented three core functions to handle camera geometry and ray generation:

  • transform(c2w, x_c): Transforms points from camera space to world space using the camera-to-world matrix. Handles both single and batched transformations by converting to homogeneous coordinates and applying the 4×4 transformation matrix.
  • pixel_to_camera(K, uv, s): Inverts the pinhole projection to recover 3D camera-space points from 2D pixel coordinates. Given the intrinsic matrix K and depth s, computes: x_c = s * (u - o_x) / f_x, y_c = s * (v - o_y) / f_y, z_c = s.
  • pixel_to_ray(K, c2w, uv): Combines the above to generate rays. For each pixel, computes the ray origin (camera position from c2w[:3, 3]) and normalized ray direction by transforming a camera-space point at depth s=1 to world space and normalizing the vector from origin to that point.

Part 2.2 — Sampling

I implemented sample_points_along_rays(ray_o, ray_d, near, far, n_samples, perturb) to sample 3D points along each ray. The function:

  • Creates uniform depth values: t = linspace(near, far, n_samples)
  • Optionally adds stratified perturbation during training to prevent overfitting to discrete sample locations
  • Computes 3D points: x = ray_o + ray_d * t for each depth value
  • Returns both the 3D points and their depth values (z_vals) for later use in volume rendering

For the Lego scene, I used near = 2.0, far = 6.0, and n_samples = 64 points per ray. The stratified sampling with perturbation helps the network learn a continuous representation rather than memorizing specific sample locations.

Part 2.3 — Putting the Dataloading All Together

I created a RaysData class that precomputes and stores all rays from the training images:

  • Initialization: For each training image, generates a grid of pixel coordinates, computes rays using pixel_to_ray, and stores ray origins, directions, and target RGB colors. This precomputation speeds up training significantly.
  • Sampling: The sample_rays(N) method randomly samples N rays from the precomputed set, returning ray origins [N, 3], directions [N, 3], and target colors [N, 3].
  • Total rays: With 100 training images of 200×200 pixels, the dataset contains 4,000,000 rays. Each training iteration samples 10,000 random rays for efficient batch processing.

Part 2.4 — Neural Radiance Field

The NeRF MLP (NeRFMLP) takes 3D positions and viewing directions as input and predicts density and RGB color:

Architecture Details

  • Positional Encoding:
    • 3D positions: L=10 frequencies → 63-dimensional encoding (3 × (1 + 2×10))
    • View directions: L=4 frequencies → 27-dimensional encoding (3 × (1 + 2×4))
    • Formula: PE(x) = [x, sin(2⁰πx), cos(2⁰πx), ..., sin(2^(L-1)πx), cos(2^(L-1)πx)]
  • Main Branch: 8 fully-connected layers of 256 neurons with ReLU activation
  • Skip Connection: After the 4th layer, concatenate the original positional encoding of x
  • Density Output: Linear(256 → 1) → ReLU (ensures positive density values)
  • RGB Output: Linear(256 → 256) → Concatenate with PE(direction) → Linear(256+27 → 128) → ReLU → Linear(128 → 3) → Sigmoid (ensures [0,1] range)
Parameters 595,844
Hidden dim 256
Layers 8 (with skip at 4)
Position PE L=10 (63-dim)
Direction PE L=4 (27-dim)

Part 2.5 — Volume Rendering

I implemented volume rendering in PyTorch using the standard NeRF formulation. For each ray, the final pixel color is computed as:

Ĉ(r) = Σᵢ Tᵢ (1 − exp(−σᵢ δᵢ)) cᵢ, where Tᵢ is the accumulated transmittance before sample i.

I verified my implementation against the provided reference test, ensuring that the compositing behavior matched.
